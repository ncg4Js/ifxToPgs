# Informix vs PostgreSQL — DDL comparison

Same database ("Fruits by Vendor") written twice: once in Informix SQL/SPL, once in PostgreSQL SQL/PL/pgSQL.

Three tables — `fruits`, `vendors`, `fruits_by_vendor` — with a cascade delete implemented deliberately via a trigger calling a routine, rather than via a foreign key `ON DELETE CASCADE`.

---

## 1. Creating and entering the database

| | Informix | PostgreSQL |
|---|---|---|
| Create | `CREATE DATABASE fruits WITH LOG;` | `CREATE DATABASE fruits;` |
| Effect on session | Becomes the current database immediately | No effect — session stays where it was |
| Switch | `DATABASE fruits;` | `\c fruits` (psql meta-command) |
| Drop | `DROP DATABASE fruits;` | `DROP DATABASE fruits;` — cannot drop the one you are connected to |

**The critical difference.** In Informix, `CREATE DATABASE` connects you to the new database. In PostgreSQL it does not. A PostgreSQL script that creates a database and then carries straight on with `CREATE TABLE` builds everything in the *previous* database, silently and without error.

PostgreSQL also has no connectionless mode — every session is bound to one database at connect time. So `CREATE DATABASE` must itself be issued from inside an existing database, conventionally `postgres`.

Correct PostgreSQL shape:

```sql
\set ON_ERROR_STOP on            -- stop at the first error instead of carrying on

\c postgres                      -- connect to the postgres database
DROP DATABASE IF EXISTS fruits;  -- safe now: we are not inside fruits
CREATE DATABASE fruits;          -- creates it; we are STILL on postgres
\c fruits                        -- NOW switch into fruits

-- every CREATE TABLE, function, trigger and INSERT goes below this line
```

Without the `\c fruits`, everything after `CREATE DATABASE` is built in whatever database the session was already on. No error, no warning.

### `\c` and its Informix equivalents

`\c` fills the role of `DATABASE` / `CONNECT TO`, with one important difference: **it is a psql client command, not SQL.**

| Informix | psql |
|---|---|
| `DATABASE fruits;` | `\c fruits` |
| `CONNECT TO 'fruits@server';` | `\c fruits user host port` |
| `CLOSE DATABASE;` | no direct equivalent |

`\c` takes up to four positional arguments — database, user, host, port — reusing the current value for any omitted. `\c - pguser` switches user and keeps the database.

Mechanically it behaves like `CONNECT TO`: psql closes the current connection and opens a new one.

Two consequences:

- **Not portable.** Informix `DATABASE` and `CONNECT TO` are language statements and work inside a 4GL program. `\c` works only in psql. A `.sql` file containing it cannot be run through Genero, JDBC, or any other client — those choose the database in the connection string.
- **Executes immediately**, ahead of any SQL still unterminated in the query buffer. This is the same mechanism behind the `postgres-#` problem in §9.

`WITH LOG` on the Informix side has no PostgreSQL equivalent — Postgres is always logged and always transactional.

## 2. Named constraints — the clause order is reversed

**Informix** puts the constraint type first and the name last:

```sql
PRIMARY KEY (entryid) CONSTRAINT pk_fruits,
UNIQUE (fruit_name)   CONSTRAINT uq_fruits_name,
FOREIGN KEY (fruit_id) REFERENCES fruits(entryid) CONSTRAINT fk_fbv_fruit
```

**PostgreSQL** puts the `CONSTRAINT` keyword and name first:

```sql
CONSTRAINT pk_fruits      PRIMARY KEY (entryid),
CONSTRAINT uq_fruits_name UNIQUE (fruit_name),
CONSTRAINT fk_fbv_fruit   FOREIGN KEY (fruit_id) REFERENCES fruits(entryid)
```

PostgreSQL follows the ISO standard here; the Informix form is proprietary. This is a pure syntax error if carried over — it will not parse, so at least it fails loudly.

## 3. Auto-increment columns

| | Informix | PostgreSQL |
|---|---|---|
| Legacy keyword | `SERIAL` (4-byte), `SERIAL8` / `BIGSERIAL` (8-byte) | `SERIAL`, `BIGSERIAL` |
| Modern form | — | `INTEGER GENERATED BY DEFAULT AS IDENTITY` |
| Implementation | Property of the table | Implicit sequence owned by the column |
| Explicit value | Accepted (0 means "generate") | Depends on `ALWAYS` vs `BY DEFAULT` |

`SERIAL` parses in both, which makes it easy to carry over unchanged — as this script does. It works, but PostgreSQL now steers new work toward identity columns.

Informix quirk worth remembering: inserting `0` into a SERIAL column means "generate the next value". In PostgreSQL, `0` is just zero.

## 4. The `rowid` column — present in PostgreSQL, absent in Informix

The Informix script has no `rowid` column. It does not need one: **Informix provides `ROWID` as an implicit pseudo-column on every non-fragmented table.**

PostgreSQL has no equivalent. `oid` on user tables was removed in PostgreSQL 12, and `ctid` is not a substitute — it changes on every UPDATE under MVCC, and slots are reused after VACUUM, so a stale value can match the wrong row.

Hence the extra column in the PostgreSQL version:

```sql
rowid BIGINT GENERATED ALWAYS AS IDENTITY
```

Four rules attach to it, from the Professional Services migration standard:

1. **Last column in the table, always.** Positional binding with right-truncation depends on it.
2. **`bigint`, not `integer`.** Informix 15 with large tables defines ROWID as 8-byte.
3. **`GENERATED ALWAYS`, not `BY DEFAULT`.** `ALWAYS` rejects an explicitly supplied value and raises; `BY DEFAULT` accepts it and persists corrupted data. This is the only automatic protection in the arrangement.
4. **Omit from the `.sch`** so `RECORD LIKE table.*` does not contain a `rowid` field.

Plus, outside the DDL: set `dbi.database.<dsname>.ifxemul.rowid = false` on every PostgreSQL datasource, and apply DDL from `psql` / `pg_restore` / Flyway rather than from a Genero program. With the emulation left on, the `rowid` token in `CREATE TABLE` is rewritten and the column is physically created as `oid` — silently.

## 5. Stored routines

### Informix SPL

```sql
CREATE PROCEDURE fn_delete_fruit_cascade(p_fruit_id INTEGER)

    DELETE FROM fruits_by_vendor
    WHERE fruit_id = p_fruit_id;

END PROCEDURE;
```

- Body is inline. No language declaration — SPL is the only built-in option.
- Terminated with `END PROCEDURE;`.
- Parameters are used directly by name.

### PostgreSQL PL/pgSQL

```sql
CREATE OR REPLACE FUNCTION fn_delete_fruit_cascade() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    DELETE FROM fruits_by_vendor
    WHERE fruit_id = OLD.entryid;
    RETURN OLD;
END;
$$;
```

- `LANGUAGE` is mandatory — PostgreSQL supports several procedural languages and has no default.
- The body is a **string literal**, conventionally dollar-quoted with `$$`. Use a tagged form (`$proc$ ... $proc$`) if the body itself contains `$$`.
- Block structure is `BEGIN ... END;`, terminated by the closing quote and a semicolon: `$$;`.
- **Takes no parameters**, and reads `OLD.entryid` instead. See §6.

### Procedural languages available in PostgreSQL

| Language | Availability | Trusted |
|---|---|---|
| PL/pgSQL | Installed by default | Yes |
| PL/Perl | contrib, `CREATE EXTENSION plperl` | Yes (`plperlu` is not) |
| PL/Tcl | contrib | Yes (`pltclu` is not) |
| PL/Python | contrib, `plpython3u` only | No — superuser only |
| SQL | Built in, `LANGUAGE sql` | n/a — not a PL |
| C | Built in | No |
| PL/Java, PL/V8, PL/R, PL/Rust, PL/Lua | Third party | Varies |

*Trusted* means sandboxed — no filesystem or network access — so any user may create functions in it. Untrusted languages are superuser-only.

Check what a server has: `SELECT lanname, lanpltrusted FROM pg_language;`

## 6. Triggers

### Informix

```sql
CREATE TRIGGER trg_fruits_cascade_delete
    DELETE ON fruits                  -- no timing keyword needed
    REFERENCING OLD AS pre            -- you choose the alias name
    FOR EACH ROW
    (EXECUTE PROCEDURE                -- action wrapped in parentheses
        fn_delete_fruit_cascade(pre.entryid));   -- column value passed as argument
```

### PostgreSQL

```sql
CREATE TRIGGER trg_fruits_cascade_delete
    AFTER DELETE ON fruits            -- BEFORE / AFTER / INSTEAD OF is mandatory
    FOR EACH ROW
    EXECUTE FUNCTION                  -- FUNCTION, not PROCEDURE; no parentheses
        fn_delete_fruit_cascade();    -- no arguments — the function reads OLD itself
```

Five differences:

| # | Informix | PostgreSQL |
|---|---|---|
| 1 | Timing keyword optional — `DELETE ON` is complete | `BEFORE`, `AFTER` or `INSTEAD OF` is **required** |
| 2 | `REFERENCING OLD AS pre` — you name the aliases | `OLD` and `NEW` are automatic and cannot be renamed |
| 3 | `EXECUTE PROCEDURE` | `EXECUTE FUNCTION` (`EXECUTE PROCEDURE` accepted but deprecated) |
| 4 | Action wrapped in parentheses | No parentheses |
| 5 | **Column values passed as arguments** — `fn(pre.entryid)` | **No arguments possible** — read `OLD.entryid` inside the body |

Point 5 is the one that forces a rewrite rather than a translation.

### OLD and NEW — where the row values come from

Both databases give a row trigger access to the row before and after the change. They deliver it differently, and that difference is why the routine signature changes.

**Informix — you declare the aliases, and pass values as arguments.**

```sql
REFERENCING OLD AS pre, NEW AS post
```

The names are yours to choose — `pre`, `post`, `old_row`, anything. Having named them, you reference columns through them (`pre.entryid`) and **pass them into the routine as ordinary parameters**. The routine is a normal procedure with a normal parameter list:

```sql
CREATE PROCEDURE fn_delete_fruit_cascade(p_fruit_id INTEGER)
```

It knows nothing about triggers. It could be called from anywhere.

**PostgreSQL — the variables are automatic, and there are no arguments.**

`OLD` and `NEW` simply exist inside a trigger function. They are not declared, cannot be renamed, and cannot be passed in. The function takes an empty parameter list and reads them directly:

```sql
CREATE FUNCTION fn_delete_fruit_cascade() RETURNS trigger   -- no parameters
...
WHERE fruit_id = OLD.entryid;                               -- read directly
```

Consequence: the function is **bound to trigger use**. It cannot be called from ordinary SQL, because outside a trigger context `OLD` and `NEW` do not exist.

**Which are populated depends on the event** — same in both databases:

| Event | OLD | NEW |
|---|---|---|
| INSERT | not set | the row being inserted |
| UPDATE | the row before | the row after |
| DELETE | the row being deleted | not set |

In PL/pgSQL the unset one is NULL, so a function handling several events must check `TG_OP` before touching either.

**Other automatic variables PostgreSQL provides** (no Informix equivalent):

| Variable | Contains |
|---|---|
| `TG_OP` | `'INSERT'`, `'UPDATE'`, `'DELETE'`, `'TRUNCATE'` |
| `TG_TABLE_NAME` | the table the trigger fired on |
| `TG_WHEN` | `'BEFORE'`, `'AFTER'`, `'INSTEAD OF'` |
| `TG_ARGV[]` | static string arguments fixed at CREATE TRIGGER time |

`TG_ARGV` is the nearest thing to passing arguments, but the values are **constants set when the trigger is created**, not per-row data. It cannot carry `OLD.entryid`.

Because of `TG_OP` and `TG_TABLE_NAME`, one PostgreSQL function can serve several triggers on several tables. The Informix pattern — pass the values in, keep the routine generic — achieves something similar by different means.

**`REFERENCING` does exist in PostgreSQL**, but means something else entirely: transition *tables* on statement-level triggers (`REFERENCING OLD TABLE AS ...`), giving the whole set of affected rows rather than one. Unrelated to the Informix row-alias usage.

### Return values

`RETURN OLD` matters: a row-level trigger function must return something.

| Trigger | Return value |
|---|---|
| `BEFORE`, row-level | Returning NULL **cancels the operation**. Returning a row lets it proceed — and for INSERT/UPDATE, the returned row is what actually gets written. |
| `AFTER`, row-level | Ignored, but must still be present. |
| Statement-level | Ignored. |

Returning the row is the safe habit. Informix has no equivalent — an SPL trigger action cannot veto the statement this way; you raise an exception instead.

## 7. DROP statements

| Object | Informix | PostgreSQL |
|---|---|---|
| Trigger | `DROP TRIGGER IF EXISTS trg_name;` | `DROP TRIGGER IF EXISTS trg_name ON fruits;` |
| Routine | `DROP PROCEDURE IF EXISTS fn(INTEGER);` | `DROP FUNCTION IF EXISTS fn();` |
| Table | `DROP TABLE IF EXISTS t;` | `DROP TABLE IF EXISTS t;` |

**Triggers.** PostgreSQL scopes trigger names to a table, not to the schema — two tables can each have a trigger called `trg_audit`. So `ON table` is required to identify one. Informix trigger names are database-wide, so the name alone is enough.

**Routines.** Procedures and functions are schema-level objects in both. A table is never part of their identity, even when all they touch is that one table — so `ON fruits` on a `DROP PROCEDURE` is wrong.

**`DROP PROCEDURE` will not remove a function** in PostgreSQL, and vice versa. They are distinct object types, and `IF EXISTS` reports a NOTICE and skips rather than failing — so a mismatched drop leaves the old object in place and looks like it worked. `DROP ROUTINE` matches either.

The signature also has to match. `fn_delete_fruit_cascade(INTEGER)` will never match the PostgreSQL trigger function, which takes no arguments.

## 8. Procedure vs Function

### The general distinction

| | Function | Procedure |
|---|---|---|
| Returns a value | Yes | No |
| Invoked as | Part of an expression | A statement in its own right |
| Typical use | Compute and give back a result | Perform an action |

### In Informix SPL

Both exist, and the boundary is loose. `CREATE FUNCTION` requires a `RETURNING` clause; `CREATE PROCEDURE` does not. In practice Informix treats them almost interchangeably, and `EXECUTE PROCEDURE` will run a function.

Where it bites is triggers. The header comment in the Informix script records it:

> Implemented as a PROCEDURE (not a value-returning FUNCTION) because Informix trigger actions cannot consume a routine's return value — an EXECUTE FUNCTION with an unconsumed result raises error **-684** ("returns too many values") when invoked from a trigger.

So on Informix, a trigger action must be a procedure, or a function whose result is consumed.

### In PostgreSQL

The distinction is strict, and inverted relative to Informix for this use case.

**Functions** — `CREATE FUNCTION`. Return a value (possibly `void`). Called in an expression: `SELECT fn(...)`. Run inside the caller's transaction and **cannot** issue `COMMIT` or `ROLLBACK`.

**Procedures** — `CREATE PROCEDURE`. Return nothing. Called with `CALL fn(...)`. **Can** issue `COMMIT` and `ROLLBACK` in the body, provided the `CALL` is not already inside an outer transaction block. Added in PostgreSQL 11 — before that, functions were the only option.

Transaction control is the main reason to choose a procedure. If you do not need it, use a function.

### The rule that decides it here

**A PostgreSQL trigger must call a function returning type `trigger`. A procedure cannot be used as a trigger action at all.**

So the Informix reasoning reverses completely:

| | Informix | PostgreSQL |
|---|---|---|
| Trigger action must be | a PROCEDURE (or a consumed function) | a FUNCTION `RETURNS trigger` |
| Reason | Unconsumed return value → error -684 | Procedures are not valid trigger actions |

The `fn_` prefix in this script is a leftover from a naming convention that no longer matches what the object is on either side. Worth renaming if the script is kept.

## 9. Gotchas encountered

Things that went wrong in practice, with the cause.

**`postgres-#` instead of `postgres=#`.** The `-#` prompt means psql is waiting for a statement terminator — the previous line had no semicolon. Meta-commands like `\i` are processed immediately and jump ahead of the buffered SQL, so a script can run while a `DROP DATABASE` is still pending. `\r` clears the buffer.

**`database "pguser" does not exist`.** No `-d` given, so psql defaulted the database name to the username. Authentication had already succeeded at that point — the failure is later, at database selection.

**`NOTICE: procedure ... does not exist, skipping`.** `DROP PROCEDURE` against an object created as a FUNCTION. `IF EXISTS` skips quietly, the old object survives, and `CREATE OR REPLACE` masks it.

**Everything created in the wrong database.** `CREATE DATABASE` without a following `\c`. No error at any point.

**No `ON_ERROR_STOP`.** psql prints an error, continues to the next statement, and exits 0. A broken script looks successful. Set `\set ON_ERROR_STOP on` at the top of every script.

## 10. Running scripts in psql

| Context | Command |
|---|---|
| From the shell | `psql -h host -U user -d db -f script.sql` |
| Inside psql | `\i script.sql` |
| Relative to the running script | `\ir other.sql` |
| Stop on first error | `\set ON_ERROR_STOP on`, or `-v ON_ERROR_STOP=1` |

`CREATE DATABASE` cannot run inside a transaction block — so do not use `psql -1` on a script that contains one.

`\c` and `\i` are psql meta-commands, not SQL. A script that relies on them cannot be run through any other client, including a Genero program or a JDBC tool.

## 11. Quick reference

| Feature | Informix | PostgreSQL |
|---|---|---|
| Create + enter database | `CREATE DATABASE` connects you | `CREATE DATABASE` then `\c` |
| Named constraint | `PRIMARY KEY (c) CONSTRAINT name` | `CONSTRAINT name PRIMARY KEY (c)` |
| Auto-increment | `SERIAL`, `SERIAL8` | `SERIAL`, or `GENERATED ... AS IDENTITY` |
| Row identifier | `ROWID` pseudo-column, implicit | None — add an identity column |
| Routine language | SPL, implicit | `LANGUAGE plpgsql` etc., mandatory |
| Routine body | Inline, `END PROCEDURE;` | Dollar-quoted string, `BEGIN ... END; $$;` |
| Trigger timing | Optional | Mandatory |
| Trigger row alias | `REFERENCING OLD AS x` — you name it | Automatic `OLD` / `NEW`, cannot rename |
| Row values reach the routine by | Being passed as arguments | Being read from `OLD` / `NEW` inside it |
| Routine reusable outside triggers | Yes | No — bound to trigger context |
| Trigger context info | — | `TG_OP`, `TG_TABLE_NAME`, `TG_WHEN`, `TG_ARGV` |
| Cancel the operation | Raise an exception | `RETURN NULL` from a `BEFORE` trigger |
| Trigger action | `EXECUTE PROCEDURE fn(args)` | `EXECUTE FUNCTION fn()`, no args |
| Trigger action type | PROCEDURE | FUNCTION `RETURNS trigger` |
| Drop trigger | Name only | Name + `ON table` |
