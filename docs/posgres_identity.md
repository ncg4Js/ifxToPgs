# PostgreSQL — Identity Columns

Source: PostgreSQL 18 documentation, §5.3 Identity Columns
<https://www.postgresql.org/docs/current/ddl-identity-columns.html>

---

## Definition

An identity column is a column whose values are generated automatically from an **implicit sequence**. It is intended for generating key values.

The sequence is created and owned by the table. It is not declared separately, and it is dropped with the column.

---

## Syntax

```sql
CREATE TABLE people (
    id bigint GENERATED ALWAYS AS IDENTITY,
    ...
);
```

or

```sql
CREATE TABLE people (
    id bigint GENERATED BY DEFAULT AS IDENTITY,
    ...
);
```

Sequence properties (start, increment, cache, etc.) can be set at creation time via `CREATE TABLE`, or changed afterwards via `ALTER TABLE`.

---

## Insert behaviour

If no value is supplied for the identity column, the implicit sequence supplies one.

```sql
INSERT INTO people (name, address) VALUES ('A', 'foo');
INSERT INTO people (name, address) VALUES ('B', 'bar');
```

```
 id | name | address
----+------+---------
  1 | A    | foo
  2 | B    | bar
```

The keyword `DEFAULT` can be used in place of a value to request the generated value explicitly. This works in `UPDATE` as well as `INSERT`.

```sql
INSERT INTO people (id, name, address) VALUES (DEFAULT, 'C', 'baz');
```

In many respects an identity column behaves like a column with a default value.

---

## ALWAYS vs BY DEFAULT

The clause determines how an explicitly supplied value is handled.

| Clause | Explicit value in INSERT | Effect |
|---|---|---|
| `GENERATED ALWAYS` | Rejected unless the statement specifies `OVERRIDING SYSTEM VALUE` | Protection against accidentally inserting an explicit value |
| `GENERATED BY DEFAULT` | Accepted; the user-specified value takes precedence | Behaves like an ordinary default value |

---

## Properties and constraints

- The data type must be one supported by sequences (see `CREATE SEQUENCE`).
- An identity column is automatically marked `NOT NULL`.
- **An identity column does not guarantee uniqueness.** A sequence normally returns unique values, but it can be reset, and values can be inserted manually. Uniqueness must be enforced with a `PRIMARY KEY` or `UNIQUE` constraint.

---

## Inheritance and partitioning

**Table inheritance** — identity columns and their properties in a child table are independent of the parent. A child does not inherit identity columns automatically. During `INSERT` or `UPDATE`, a column is treated as an identity column only if it is one in the table named in the statement.

**Partitioning** — partitions *do* inherit identity columns from the partitioned table. Partitions cannot have their own. Identity properties are consistent across the whole partition hierarchy.

# Notes — relevance to the Genero ROWID / PostgreSQL migration standard

These are annotations, not part of the PostgreSQL documentation.

## 1. Why `GENERATED ALWAYS` is specified in the standard

The standard mandates `ALWAYS`, not `BY DEFAULT`, for the `rowid` column, and calls it the only automatic protection in the arrangement.

This page is the underlying reason. `ALWAYS` rejects an explicitly supplied value; `BY DEFAULT` accepts it silently. Since the whole scheme relies on positional binding with right-truncation, a misaligned write-back under `BY DEFAULT` would persist corrupted data with `sqlcode = 0`. Under `ALWAYS` the misaligned write is refused and raises.

## 2. `OVERRIDING SYSTEM VALUE` is an escape hatch

`ALWAYS` is not absolute. A statement specifying `OVERRIDING SYSTEM VALUE` can still supply an explicit value.

Worth flagging: nothing prevents someone from adding that clause to a data-load or fix-up script, which would defeat the tripwire. It is not reachable from ordinary Genero SQL, but it is reachable from `psql` and from migration tooling.

## 3. Identity does not imply unique

The standard uses `rowid` as a row identifier in `UPDATE ... WHERE rowid = ?`. This page is explicit that identity alone does not guarantee uniqueness — only `PRIMARY KEY` or `UNIQUE` does.

In practice the sequence will not collide on its own. The exposure is a sequence reset, or a restore that repopulates the table. Adding a `UNIQUE` constraint on `rowid` would close this at negligible cost, and is not mentioned in the standard.

## 4. `bigint` is consistent with this page

The standard requires `bigint` rather than `integer`, citing Informix 15 large-tables ROWID being 8 bytes. Nothing on this page conflicts: any sequence-supported type is permitted.

## 5. Sequence properties are adjustable after the fact

`ALTER TABLE` can change the properties of the implicit sequence. Relevant if a migration needs to start `rowid` values above the range already in use on the Informix side, to keep values from overlapping during a phased cutover.

## 6. Partitioning caveat

If any customer table is partitioned, partitions inherit the identity column from the parent and cannot define their own. This interacts with the standard's "`rowid` must be the last column in every table" rule — the build-gate assertion in §7 queries `pg_class` with `relkind = 'r'`, which does not match partitioned tables (`relkind = 'p'`). Partitioned schemas would slip past that check.

## 7. Not covered here

This page says nothing about retrieving the generated value. That is `currval` / `pg_get_serial_sequence` / `RETURNING`, documented elsewhere, and is where the standard's `last_rowid()` wrapper lives.
